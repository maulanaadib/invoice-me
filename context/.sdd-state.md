## Stage 0: Framing
- Product name: invoice-me (brand sementara dari master prompt: InvoiceFlow)
- One line description: Platform invoice self-hosted multi-tenant: buat, kelola, dan ekspor invoice profesional (DP/Pelunasan/Termin) dengan live preview A4 dan PDF.
- MVP boundary: MVP = seluruh acceptance criteria master prompt bagian 35 (40 poin) terpenuhi: multi-tenant + invoice engine + PDF + super admin + audit log + Docker. Bukan demo AI: tiap tombol harus benar-benar bekerja. QRIS, SMTP forgot-password, multi-currency, analytics produk, e-meterai resmi (autopristine) = defer.
- Primary audience: Pemakaian sendiri dulu (tim internal, multi-organization), nanti publik sebagai SaaS self-hosted.
- Monetization: Belum / gratis dulu untuk first build. Struktur SaaS-aware (multi-tenant), billing tidak masuk MVP.
- Success metric: User signup & retention.
- Hard constraints: Hasil maksimal + secepat masuk akal (tidak ada deadline keras). Self-hosted (Coolify + Docker Compose). UI Bahasa Indonesia, locale id-ID, timestamp DB UTC, timezone bisnis Asia/Jakarta. Bahasa kode English. Modular monolith + 1 service terpisah pdf-service.

## Stage 1: Capabilities
- In scope: authentication (username/email + password, no public registration), multi-tenant orgs (Organization + Membership + role OWNER/ADMIN/STAFF/VIEWER), file upload (logo, tanda tangan, PO reference, payment proof), search (server-side pagination + filter di invoice list), admin panel (super admin), AI features: none.
- Deferred: payments/billing (modul PEMBAYARAN internal untuk status invoice tetap masuk; tapi payment gateway/billing SaaS = defer), email/notifications (SMTP forgot-password structurally prepared only — halaman menjelaskan "hubungi admin"; email notification defer), realtime collaboration (none), public API (none), offline support (none), internationalization (hardcode id-ID untuk MVP), QRIS (fase berikutnya).

## Stage 2: Cross cutting
- SEO: Not applicable — auth-walled internal app, tidak ada marketing page public. Hanya perlu robots.txt + noindex default.
- Performance: Core Web Vitals bukan prioritas utama; invoice list harus cepat dengan pagination server-side. Live preview A4 harus smooth (single source render component, no re-render berat).
- Analytics and error monitoring: Error tracking via GlitchTip/Sentry self-hosted dari feature 01 (defer product analytics).
- Accessibility: WCAG 2.1 AA target (label form, keyboard navigation, focus visible, color contrast, aria pada custom components, jangan andalkan warna saja untuk status).
- Legal and compliance: UU PDP (Indonesia) + cookie consent + privacy policy. PII sensitif: NPWP, rekening bank, data customer.

## Stage 3: Stack
- Language and runtime: Node.js LTS (v22 major pinned), TypeScript strict (no any policy)
- Framework and rendering: Next.js App Router, server components + client islands (form editor split-screen), SSR untuk dashboard, print route internal
- Database: PostgreSQL 16
- ORM or query layer: Prisma ORM
- Local dev database: Docker Compose postgres service (docker-compose.dev.yml)
- Auth and session: Better Auth — email+password + username plugin + admin plugin; public registration dimatikan; cookie HttpOnly Secure SameSite; rate limit login + lockout
- Storage: Local persistent volume /data (uploads + invoices), interface StorageService siap diganti S3/MinIO
- Hosting: Coolify (self-hosted), Docker Compose multi-service: app + postgres + pdf-service, optional cloudflared profile
- Background jobs: Job queue internal untuk PdfJob (status, attempt, retry terbatas) — defer queue external seperti BullMQ untuk MVP
- Observability: JSON structured log ke stdout Docker + /health endpoint + GlitchTip error tracking
- Testing: Vitest (unit/integration) + Playwright Test (E2E)
- Money rule: decimal.js untuk kalkulasi + Prisma Decimal untuk persist. Nominal dari form dikirim sebagai string decimal. Semua total dihitung ulang server-side, tidak percaya total client. PPN tidak di-hardcode satu persentase.
- Timezone rule: Timestamp DB UTC; tampilan & laporan pakai Asia/Jakarta; locale id-ID. Hari kerja/periode tagihan diinterpretasi WIB.

## Stage 3b: Architecture shape
- Architecture style: Modular monolith (app) + 1 service terpisah pdf-service (Playwright Chromium). Sesuai master prompt.
- Module boundaries: src/modules/{auth, organizations, customers, projects, invoices, payments, pdf, storage, audit} — satu feature menyentuh satu modul. src/components/{ui, invoice, forms, tables, layout}, src/lib, src/server, src/types.
- Split triggers: Split hanya pada measured evidence (team boundary, scaling bottleneck, independent deploy need), never anticipated scale. pdf-service sudah terpisah karena Playwright runtime isolasi.
- Dependency direction: modules → lib/server layer; tidak ada modul mengimpor internal modul lain; UI components stateless menerima props.

## Stage 3c: Security
- Auth and session: Better Auth, login username/email + password, session cookie HttpOnly+Secure+SameSite, remember session, logout, rate limit + lockout, force password change (first login / admin reset), admin create user dengan temporary password, public sign-up disabled.
- Authorization model: Central permission service. Platform role SUPER_ADMIN. Org role OWNER/ADMIN/STAFF/VIEWER (matrix hak akses master prompt bagian 3). Org scoping wajib di setiap query/mutation. Cegah IDOR. Audit log untuk semua aksi sensitif.
- Input validation: Zod di boundary (form + API route handler), sebelum logic runs. Upload: MIME sniffing dari isi file, max 2MB, random filename, path traversal prevention.
- Secrets: Env variables (.env.local dev, gitignored; production values di Coolify dashboard, never in repo). INTERNAL_PDF_SECRET, BETTER_AUTH_SECRET. Key enkripsi rekening dari env. Tidak ada secret di client bundle atau log line.
- Compliance scope: UU PDP (Indonesia) + cookie consent + privacy policy. GDPR fallback EU jika diperlukan nanti.
- Data protection: Nomor rekening encrypt at rest (key dari env), masked (last4) kecuali di invoice dan halaman berizin. NPWP termasuk PII. Audit metadata disanitasi (tidak simpan password/token/rekening lengkap).

## Stage 3d: Error handling
- Error response shape: Satu shape JSON konsisten { ok: boolean, data: null | {...}, error: { code: string, message: string, details?: object } }.
- Error categories: VALIDATION, NOT_FOUND, UNAUTHORIZED, FORBIDDEN, CONFLICT, RATE_LIMITED, LOCKED (invoice issued), INTERNAL. Retryable: RATE_LIMITED, INTERNAL. User-facing message plain Indonesian.
- Logging: JSON structured ke stdout (pino-style), level info/warn/error. Tidak ada secret, token, password, nomor rekening, atau PII di log line.
- Observability: GlitchTip error tracking dari feature 01; /health endpoint (db + storage + pdf-service readiness); Docker healthcheck.
- User facing errors: Bahasa Indonesia plain, no stack trace, no internal name. Field error jelas di form. Toast non-intrusive untuk aksi. Empty state + loading state di setiap halaman.

## Stage 3e: Testing
- Runners: Vitest unit/integration, Playwright Test E2E, Playwright Chromium juga untuk PDF verification.
- Test pyramid: Unit (calculation, terbilang, numbering, permission logic) — dari feature pertama yang punya logic. Integration (service layer + Prisma + test DB) — dari invoice engine. E2E (alur lengkap master prompt bagian 32) — dari invoice issue flow.
- What is tested first: Terbilang (nol, satu, sebelas, seribu, 2.250.000, angka besar), invoice calculation (full, DP, pelunasan, termin, PPN exclusive/inclusive/manual, discount, rounding, no floating point), numbering (race condition, duplicate prevention, reset policy), permission (org isolation A vs B, role matrix).
- Definition of done: Feature selesai bukan karena works, tapi karena verified against spec: Check When Done lulus, lint+typecheck lulus, unit/integration test sesuai pyramid lulus, production build lulus.

### Feature 10 — bank-signers (answered 2026-10-09)

1. **Signer module placement — keep `modules/signers`.** Build per spec Implementation item 3
   (`src/modules/signers/service.ts`). Do NOT move the file into `modules/bank-accounts`.
   `architecture-standards.md` module-table row "modules/bank-accounts | BankAccount (encrypt at
   rest), Signer" is reported stale/inconsistent for a separate bundle sync (`selcy-sync`); the
   builder does not edit `context/` standards files.
2. **Known token with an empty value → empty string.** A known placeholder whose value is absent
   (e.g. `{REFERENCE_NUMBER}` on an invoice without a PO, `{BILLING_PERCENT}` on a manual/custom
   billing invoice) resolves to `""` so a sent document never prints a literal token. Unknown
   tokens (e.g. `{FOOBAR}`) keep the spec rule: stay literal + warning in preview.
